# Требования к интерфейсу и дизайн-системе

Этот документ задаёт требования для разработки интерфейса и обязателен для агентов, работающих в репозитории.

## Выбор технологий

- Стек интерфейса: React + Tailwind CSS + shadcn/ui.
- Маршрутизация: React Router в Declarative mode (`BrowserRouter`, `Routes`, `Route`, `Outlet`, `Navigate`). Не использовать Data mode или Framework mode, route loaders и actions.
- HTTP-клиент: Axios с общим экземпляром и заменяемым фейковым адаптером.
- Работа с серверным состоянием: TanStack Query (`@tanstack/react-query`), `QueryClientProvider`, queries для чтения и mutations для входа, выхода и сброса пароля.
- Инструмент сборки: Vite; язык: TypeScript.
- Перед реализацией интерфейса проверить совместимость выбранного стека с архитектурой проекта. Если потребуется другой стек, согласовать изменение с пользователем и обновить документ.
- Компоненты shadcn/ui адаптировать под общую дизайн-систему; их наличие само по себе не подтверждает доступность.

## Структура проекта

### Где создавать код

- `src/main.tsx`: точка входа, подключение глобальных стилей и монтирование React.
- `src/app`: сборка приложения. `App.tsx` связывает провайдеры и маршрутизацию; `providers.tsx` подключает TanStack Query и тему; `router.tsx` определяет маршруты в Declarative mode; `query-client.ts` настраивает QueryClient.
- `src/api/client.ts`: общий Axios-клиент, baseURL, таймаут и подключение адаптера. Не размещать Axios-клиент в `shared`.
- `src/api/errors.ts`: общий формат и нормализация ошибок API.
- `src/api/fake`: имитация сервера. `adapter.ts` принимает запросы Axios; `auth-handlers.ts` реализует ответы авторизации; `fixtures.ts` содержит демо-данные; `session.ts` управляет демо-сессией; `scenarios.ts` задаёт воспроизводимые задержки и ошибки.
- `src/pages`: компоненты страниц, собирающие интерфейс из layouts и features. В каждой папке создавать соответствующий компонент страницы, например `login/LoginPage.tsx` и `dashboard/DashboardPage.tsx`. Не размещать здесь транспорт, фейковый API или основную бизнес-логику.
- `src/features/auth`: функциональность авторизации. `api.ts` содержит операции через общий Axios-клиент; `queries.ts` — ключи кэша и чтение текущего пользователя; `mutations.ts` — вход, выход и сброс пароля; `types.ts` — типы авторизации; `validation.ts` — правила форм; `components` — формы и защита маршрутов.
- `src/layouts`: общие оболочки страниц. `AuthLayout.tsx` оформляет страницы авторизации; `AdminLayout.tsx` содержит навигацию админки и `Outlet`.
- `src/shared/ui`: базовые компоненты shadcn/ui. Настроить генератор shadcn/ui на этот путь.
- `src/shared/components`: общие составные компоненты без привязки к конкретной функции приложения. Компоненты, специфичные для авторизации, оставлять в `features/auth/components`.
- `src/shared/lib`: общие утилиты без бизнес-логики авторизации.
- `src/styles/tokens.css`: базовая палитра и шкалы типографики, размеров, отступов, оформления и движения. `themes.css`: семантические токены светлой и тёмной тем. `globals.css`: подключение Tailwind, файлов токенов и базовые стили.
- `tests/e2e`: полные пользовательские сценарии. Модульные и компонентные тесты хранить рядом с исходниками, например `LoginForm.test.tsx`.
- `public`: статические файлы, которым нужен неизменяемый путь при сборке.

### Правила зависимостей

- `app` связывает pages, layouts, features, api и shared.
- `pages` используют layouts, features и shared; `layouts` используют features и shared.
- `features` используют общий `api` и `shared`. Формы работают через queries и mutations, не импортируют фейковый адаптер напрямую.
- `api` не импортирует app, pages, layouts или features. Если контракт нужен одновременно сервисам и фейковым обработчикам, разместить его в `src/api/contracts/`, чтобы избежать обратных зависимостей и дублирования типов.
- `shared` не импортирует app, pages, layouts, features или api.
- Перенаправления авторизации и очистку QueryClient выполнять в features или связывать на уровне app; не помещать их в Axios-клиент.
- Новые функции добавлять в `src/features/<название>`, страницы — в `src/pages/<название>`. Не создавать параллельные папки для тех же обязанностей и избегать циклических импортов.

## Фейковый API и состояние авторизации

- Реализовать фейковый адаптер на уровне Axios: компоненты вызывают сервисы API через TanStack Query, сервисы используют общий Axios-клиент, а адаптер имитирует ответы сервера без внешнего backend.
- Не подменять сетевые вызовы отдельными таймерами или захардкоженными успешными результатами внутри компонентов. Замена адаптера на настоящий API не должна требовать переписывания форм и страниц.
- Определить единый контракт запросов, ответов и ошибок для входа, получения текущего пользователя, выхода, запроса сброса пароля и установки нового пароля.
- Предусмотреть воспроизводимые демо-данные и сценарии: успешный ответ, неверные учётные данные, отсутствие сессии, истёкшая сессия, недействительный или истёкший токен сброса и ошибка сервера. Имитировать задержку, чтобы проверить состояния загрузки.
- Состояние текущего пользователя хранить в TanStack Query. Различать проверку сессии, авторизованное и неавторизованное состояния; не показывать защищённый контент до завершения проверки.
- Демо-сессию сохранять между перезагрузками страницы. Хранить только необходимые искусственные данные сессии; не сохранять введённые пароли в браузерном хранилище или логах.
- При выходе и истечении сессии очищать состояние пользователя и кэш защищённых данных, затем перенаправлять на страницу входа.
- Фейковая авторизация служит для демонстрации интерфейса. Защита маршрутов на клиенте не заменяет серверную проверку доступа в будущем реальном API.

## Маршруты и пользовательские сценарии

| Маршрут | Назначение и доступ |
| --- | --- |
| `/login` | Публичная форма входа: email и пароль |
| `/forgot-password` | Публичная форма запроса сброса пароля по email |
| `/reset-password?token=…` | Установка нового пароля по демо-токену, с подтверждением пароля |
| `/admin/dashboard` | Защищённая главная страница админки |

- После успешного входа пользователь всегда попадает на `/admin/dashboard`.
- Все маршруты `/admin/*` размещать внутри защищённого layout админки с `Outlet`. Для неавторизованного пользователя прямой переход на защищённую страницу должен вести на `/login`.
- Авторизованного пользователя со страницы входа перенаправлять на `/admin/dashboard`. Переходы авторизации выполнять с заменой записи истории, чтобы кнопка «Назад» не возвращала к завершённой форме входа.
- На dashboard показывать понятный заголовок, данные текущего демо-пользователя и доступное действие выхода. Остальное наполнение dashboard пока не определено.
- Форма входа должна валидировать обязательные поля и формат email, показывать ошибку неверных учётных данных и предотвращать повторную отправку во время запроса.
- Запрос сброса должен показывать одинаковое подтверждение для существующего и неизвестного email. Реальную почту не отправлять; в демо-режиме предоставить явный способ открыть ссылку сброса для тестового пользователя.
- Форма нового пароля должна проверять подтверждение и документированную политику пароля. После успешного сброса токен становится недействительным, прежняя сессия завершается, пользователь переходит на `/login` с сообщением об успехе и входит новым паролем.
- При отсутствующем, недействительном или истёкшем токене показывать понятную ошибку и ссылку для повторного запроса сброса.
- Для форм предусмотреть состояния загрузки, успеха, ошибок полей и ошибок API; сообщения должны быть доступны скринридеру.
- Настроить fallback хостинга на HTML приложения, чтобы прямое открытие и перезагрузка маршрутов `BrowserRouter` работали.

## Дизайн-токены

Все общие визуальные параметры должны настраиваться централизованно через CSS-переменные. Tailwind и компоненты должны использовать эти токены.

Определить следующие группы:

| Группа | Обязательные параметры |
| --- | --- |
| Цвета | Фон страницы, поверхности, основной и вторичный текст, границы, акцент, текст на акценте, ошибка, предупреждение, успех, индикатор фокуса |
| Типографика | Семейства шрифтов, шкала размеров, насыщенность, межстрочные и межбуквенные интервалы |
| Размеры и отступы | Единая шкала отступов, ширина контента, размеры элементов управления |
| Оформление | Радиусы, толщины границ, тени |
| Движение | Длительности и кривые переходов |

### Правила использования

- Разделять базовые значения палитры и шкал и семантические токены, описывающие назначение: например, `--color-text-primary`, `--color-surface`, `--color-focus-ring`.
- Компоненты должны обращаться к семантическим токенам. Не дублировать произвольные цвета, размеры шрифтов, радиусы и отступы в компонентах.
- При необходимости вводить токены компонентов, ссылающиеся на общие семантические токены.
- Хранить базовые определения в `src/styles/tokens.css`, а семантические значения тем — в `src/styles/themes.css`, согласно структуре проекта.
- Настроить интеграцию с установленной версией Tailwind и существующими CSS-переменными shadcn/ui. Не создавать конкурирующие источники значений.
- Предусмотреть светлую и тёмную темы через переопределение токенов, без дублирования компонентов.
- Централизовать типографические роли: заголовки, основной текст, подписи и текст элементов управления.
- При добавлении токена документировать его назначение. Исключения для специфической геометрии или контента должны быть локальными и обоснованными.

## Доступность

Целевой уровень интерфейса — WCAG 2.2 AA.

- Использовать семантическую HTML-разметку и доступные имена элементов управления.
- Обеспечить полную работу с клавиатуры, логичный порядок переходов и видимый, не перекрытый фокус.
- Соблюдать контраст текста: минимум 4.5:1 для обычного текста и 3:1 для крупного текста по определению WCAG. Для значимых границ элементов управления и графических объектов — минимум 3:1 с соседними цветами.
- Не передавать смысл исключительно цветом. Ошибки и статусы должны иметь текстовое объяснение.
- Формы должны иметь связанные подписи, понятные инструкции и доступные сообщения об ошибках.
- Диалоги и другие составные компоненты должны корректно управлять фокусом и поддерживать ожидаемые клавиатурные взаимодействия.
- Поддерживать масштабирование текста, адаптивное расположение и требования к размерам целей взаимодействия WCAG 2.2 AA.
- Учитывать `prefers-reduced-motion` и отключать необязательное движение.
- Проверять доступность и контраст отдельно для обеих тем и интерактивных состояний.

## Проверка результата

- Изменение общих токенов должно менять связанные компоненты без редактирования их исходного кода.
- Для элементов управления предусмотреть применимые состояния: обычное, наведение, фокус, нажатие, отключение, ошибка и загрузка.
- Перед завершением интерфейсной задачи выполнить доступные проверки сборки и типов, а также релевантные существующие тесты.
- При реализации авторизации проверить успешный и неуспешный вход, переход на dashboard, прямой доступ к защищённому маршруту, восстановление сессии после перезагрузки, выход и истечение сессии.
- Проверить полный сценарий сброса пароля: запрос, демо-ссылка, ошибки токена, несовпадение паролей, успешная смена, отказ старого пароля, вход новым паролем и невозможность повторно использовать токен. Проверить очистку защищённого кэша и отсутствие повторных отправок форм.
- Проверить основные пользовательские сценарии с клавиатуры, адаптивное отображение, контраст и работу со скринридером. Автоматические проверки доступности дополняют ручные.
- В отчёте отделять выполненные проверки от невыполненных. Не заявлять соответствие WCAG только на основании выбранной библиотеки или автоматического сканирования.
